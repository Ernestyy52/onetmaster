# ภารกิจ: พัฒนา onetmaster เป็น MMORPG

ใช้ไฟล์นี้เป็น **Claude Code custom agent** โดยคัดลอกไปที่ `.claude/agents/onetmaster-mmorpg.md` ภายในรีโป แล้วเปิด Claude Code จากรากรีโปด้วย `claude --agent onetmaster-mmorpg --effort medium "เริ่มงานถัดไปตามแผน"` หากใช้ Claude Code รุ่นที่รองรับการกำหนด `model` และ `effort` รายการเรียก subagent (v2.1.292 ขึ้นไป) ให้ทำตามตาราง Routing ด้านล่าง หากรุ่นเก่ากว่า ให้ทำงานหลักด้วย Sonnet/medium และแจ้งข้อจำกัดสั้น ๆ ห้ามอ้างว่าได้สลับโมเดลแล้วทั้งที่ไม่ได้สลับจริง

## เป้าหมายและข้อจำกัด

พัฒนาเกมในรีโป `https://github.com/Ernestyy52/onetmaster` จาก RPG สอน O-NET ป.6 เป็น MMORPG Pixel Isometric ที่ยังคงชื่อโลก **หอคอยสี่วิชา** และจุดเด่นด้านการเรียนรู้ อ้างอิง *วงจรการเล่น* ของเกมแฟนตาซีออนไลน์คลาสสิก ได้แก่ สร้างตัวละคร เปลี่ยนอาชีพ สำรวจพื้นที่ล่า ทำเควสต์ สะสมไอเทม เล่นกับเพื่อน ลงดันเจียน และทำบอส ห้ามคัดลอกชื่อ ตัวละคร แผนที่ ภาพ เพลง UI หรือ asset เฉพาะของ Ragnarok

สิ่งที่มีอยู่ตาม README/handoff ณ 15 พฤศจิกายน 2569: Phaser 3.90 + TypeScript + React 18 + Vite 6, ลานกลาง Isometric และทางแยกสี่วิชา, การเดินหลายรูปแบบ, ภารกิจบทนำถึงเลเวล 3, การต่อสู้แบบผลัดกันเล่นที่ใช้โจทย์, XP/Subject Mastery/อุปกรณ์, `LocalGameApi` และเซฟใน `localStorage`, ร่าง Supabase schema, โจทย์ 24 ข้อสถานะรอครูตรวจ ตรวจโค้ดปัจจุบันก่อนลงมือเสมอ เพราะรีโปอาจเปลี่ยนไปแล้ว

## วิธีทำงานและการใช้โทเค็น

1. ทำ **หนึ่ง milestone ต่อหนึ่งรอบงาน** ตรวจ `git status` และไฟล์ที่เกี่ยวข้องก่อนแก้ อย่าเขียนระบบใหม่ทั้งโปรเจกต์หรือทำ milestone ถัดไปเอง
2. ใช้ `rg` เพื่อหาไฟล์/สัญญาที่เกี่ยวข้อง อ่าน `README.md`, `handoff.md` เฉพาะหัวข้อที่จำเป็น และอ่านโค้ดเฉพาะส่วนที่จะเปลี่ยน ไม่พิมพ์ไฟล์หรือ log ยาวลงคำตอบ
3. วางแผนสั้น ๆ ไม่เกิน 12 บรรทัด แล้วลงมือแก้จริง ใช้โครงสร้าง Phaser/React/TypeScript, Tiled, `GameApi`, shared rules, store และ tests เดิมเท่าที่เหมาะสม
4. ทำงานหลักใน session นี้ด้วย **Sonnet/medium** เปลี่ยนเส้นทางเฉพาะงานที่เข้าเกณฑ์ในตาราง Routing โดยเรียก Agent/subagent พร้อม `model` และ `effort` รายครั้ง รอผลและนำมารวม หลีกเลี่ยงการส่งงานเดียวกันให้หลาย agent หรือแก้ไฟล์เดียวกันพร้อมกัน
5. ใช้ Opus เฉพาะการตัดสินใจที่กระทบหลายระบบ การตรวจความปลอดภัย/ธุรกรรม หรือปัญหาที่ Sonnet แก้ไม่สำเร็จหลังมีวิธีทำซ้ำชัดเจน ใช้ Haiku เฉพาะข้อความ/เอกสารขอบเขตเล็ก ถ้างานเล็กจนค่าเปิด subagent ไม่คุ้ม ให้ทำใน session หลัก
6. ทดสอบเฉพาะส่วนที่เปลี่ยนก่อน แล้วรัน gate หลักหนึ่งครั้งเมื่อ milestone เสร็จ: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`, `npm run test:e2e` ตามสคริปต์ที่มีจริง บันทึกผลที่รันจริง ไม่กล่าวว่าผ่านโดยไม่มีผล
7. จบแต่ละรอบด้วยสถานะ milestone, ไฟล์หลักที่แก้, ผลทดสอบ, สิ่งที่ยังติดขัด และคำสั่งสั้น ๆ สำหรับรอบถัดไป ไม่เขียนรายงานยาวซ้ำกับเอกสารนี้

## Routing: เลือก model/effort ตามงาน

| ชนิดงาน | ผู้ทำ | Model | Effort | เงื่อนไข |
|---|---|---|---|---|
| โค้ดเกม, UI, ข้อมูลอาชีพ, tests ที่ขอบเขตชัด | session หลัก | Sonnet | medium | ค่าเริ่มต้น |
| วิเคราะห์สถาปัตยกรรมออนไลน์, การย้ายข้อมูล, ขอบเขตเซิร์ฟเวอร์ | subagent เฉพาะประเด็น | Opus | medium | เรียกครั้งเดียวต่อการตัดสินใจสำคัญ ขอผลไม่เกิน 1 หน้า |
| ปัญหาข้าม Phaser/React/API หรือบั๊กที่มีกรณีขอบหลายแบบ | subagent เฉพาะประเด็น | Sonnet | high | ใช้เมื่อมีวิธีทำซ้ำและผลตรวจเบื้องต้นแล้ว |
| ตรวจ auth, RLS, การตอบโจทย์, รางวัลซ้ำ, แข่งกันเขียนข้อมูล | subagent ตรวจสอบ | Opus | high | ก่อนปิด M2/M4 หรือเมื่อพบช่องโหว่จริง; ส่งเฉพาะ diff/schema ที่เกี่ยวข้อง |
| ปรับคำปุ่ม บทสนทนา หรือคู่มือสั้น | subagent หรือ session หลัก | Haiku | low | ใช้เมื่อมีหลายข้อความมากพอให้คุ้มค่าเปิดงานใหม่ |

ตารางนี้กำหนด **การ routing ไปยัง subagent** ไม่ใช่คำสั่งให้เปลี่ยน model ของ session หลักทุกครั้ง เอกสาร Markdown ไม่สามารถบังคับ `/model` หรือ `/effort` ของ session หลักโดยอัตโนมัติ หาก Agent tool ไม่พร้อม ให้ทำส่วนที่ปลอดภัยด้วยค่าปัจจุบันและแจ้งสิ่งที่ต้องตรวจต่อ ไม่อ้างผลการตรวจจากโมเดลอื่น

## กฎเกมที่ต้องคงไว้ทุก milestone

- ความก้าวหน้า 3 แกนแยกกัน: **Adventure Level** สำหรับการสำรวจ/เนื้อเรื่อง, **Job Level** สำหรับสกิลอาชีพ, **Subject Mastery** สำหรับทักษะภาษาไทย อังกฤษ คณิต และวิทยาศาสตร์ อุปกรณ์หรือการเติมเงินต้องไม่ทำให้ข้ามโจทย์หรือบิดผลวัดความรู้
- โจทย์ที่ใช้จริงต้องผ่านครูอนุมัติ คำถามและเฉลยอยู่ฝั่งเซิร์ฟเวอร์เมื่อเปิดออนไลน์ ห้ามส่งเฉลยก่อนตอบและห้ามใช้โจทย์ draft โดยอ้างว่าอนุมัติแล้ว
- โลกออนไลน์ต้องแยก **ข้อมูลชั่วคราว** (ตำแหน่ง/สถานะออนไลน์) จาก **ข้อมูลถาวร** (ตัวละคร ไอเทม XP ความชำนาญ เควสต์) เซิร์ฟเวอร์ยืนยันคำตอบ สกิล รางวัล และการเปลี่ยนสถานะสำคัญ การส่ง request ซ้ำต้องไม่ให้รางวัลซ้ำ
- คงการต่อสู้แบบผลัดกันเล่นและจังหวะโจทย์ที่มีอยู่ในช่วงแรก โลกที่ผู้เล่นเดินร่วมกันใช้ realtime ได้ ดันเจียนใช้ instance และปาร์ตี้ 2–4 คน การเปลี่ยนการต่อสู้ทั้งระบบเป็น real-time ต้องมีต้นแบบและเกณฑ์ทดลองก่อน
- เกมสำหรับเด็ก: ใช้ข้อความสำเร็จรูปก่อน; แชตอิสระ/การแลกเปลี่ยนผู้เล่นต้องรอระบบดูแลและนโยบายที่ชัด; ไม่แสดงคะแนนสอบรายคนต่อสาธารณะ; ไม่มี pay-to-win
- รองรับมือถือและคอม การอ่านภาษาไทย พื้นที่แตะอย่างน้อย 44×44 CSS px, safe area, Refresh/reconnect และเครื่องที่ต้องใช้ Canvas แทน WebGL

## Milestones และเกณฑ์ผ่าน

### M0 — ตรวจฐานเกมและออกแบบสัญญาข้อมูล

**งาน:** ตรวจระบบจริงใน `src/api`, `src/game`, `src/shared`, `src/state`, `src/ui`, `supabase/migrations`, tests; ระบุสิ่งที่ใช้ซ้ำได้และช่องว่างของการเล่นหลายคน กำหนดความเป็นเจ้าของข้อมูล/คำสั่งของ client และ server, โครงสร้าง character/job/skill/zone/party, วิธี migrate save, เป้าหมายผู้เล่นพร้อมกันต่อโซนและข้อสมมติเรื่องโฮสต์/ต้นทุน เขียน ADR สั้นหนึ่งไฟล์ ไม่ลงมือสร้างระบบใหญ่ใน M0

**Routing:** ขอ Opus/medium ตรวจสถาปัตยกรรมเฉพาะข้อที่ไม่ชัด แล้ว session หลักสรุปแผน

**ผ่านเมื่อ:** มีรายการสถานะจริงพร้อมชื่อไฟล์, API/schema ที่ต้องเปลี่ยน, ลำดับ migration, ความเสี่ยงและเกณฑ์ทดสอบของ M1–M4 ไม่เรียกต้นแบบ local ว่า MMO พร้อมใช้จริง

### M1 — สร้างตัวละครและระบบอาชีพ

**งาน:** ช่องตัวละคร ชื่อเล่น/ตรวจชื่อ รูปลักษณ์/ตัวอย่างก่อนยืนยัน หน้าสร้างตัวละครแบบ responsive, นักผจญภัยฝึกหัด → นักดาบ/ผู้พิทักษ์/นักเวท/นักธนู, Job Level, ค่าสถานะที่มี soft cap, สกิล active/passive ต่างบทบาท, skill UI, อุปกรณ์ที่เข้ากับอาชีพ, ตารางข้อมูลอาชีพที่เพิ่มสายขั้นสูงได้, migration เซฟเดิม ออกแบบให้ผู้เล่นเดิมมีตัวละครและความคืบหน้าเดิมโดยไม่สูญหาย

**Routing:** Sonnet/medium; Opus/medium เฉพาะถ้า migration มีทางเลือกที่กระทบข้อมูลเดิมมาก

**ผ่านเมื่อ:** ผู้เล่นใหม่สร้างตัวละครได้; ทดลองทั้ง 4 อาชีพแล้วเห็นผลสกิลต่างกัน; เส้นทางบทนำเดิมเล่นจบ; เซฟเก่า/Refresh ใช้ได้; tests และ build ผ่าน

### M2 — บัญชีและข้อมูลถาวรฝั่งเซิร์ฟเวอร์

**งาน:** Supabase Auth/PostgreSQL/Edge Functions หรือแนวทางที่ M0 พิสูจน์ว่าเหมาะสม, แยก user กับ character, เลือกตัวละคร, versioned migration, เซฟข้ามเครื่อง, RLS นักเรียน/ครู, เก็บเฉลยและกุญแจบน server, API ที่ตรวจ ownership/turn/request id, กู้สถานะหลังเน็ตหลุด มี dev setup ที่รันได้โดยไม่ฝัง secret

**Routing:** Sonnet/medium ทำโค้ด; Opus/high ตรวจ RLS, auth, ธุรกรรมและข้อมูลที่ client ปลอมได้ก่อนปิดงาน

**ผ่านเมื่อ:** บัญชีเดียวกันเห็นตัวละครบนอีกเครื่อง; บัญชีอื่นอ่าน/แก้ข้อมูลไม่ได้; ส่งคำตอบหรือรับรางวัลซ้ำไม่เพิ่ม XP/ของ; reconnect ได้; มี integration tests

### M3 — โลกออนไลน์ที่เห็นผู้เล่นจริง

**งาน:** Hub/zone ID, presence และตำแหน่งผู้เล่น, เข้า/ออกโซน, interpolation, จำกัดความถี่ส่งข้อมูล, idle/disconnect cleanup, avatar ของคนอื่น, NPC/แผนที่เดิม, capacity ต่อโซนและแนวทางแบ่ง instance/shard ห้ามใช้ bot จำลองแล้วเรียกว่า multiplayer จริง

**Routing:** Sonnet/medium; Sonnet/high เฉพาะปัญหาซิงก์/ประสิทธิภาพที่มีวิธีทำซ้ำ

**ผ่านเมื่อ:** เปิดสองบัญชีในสองเบราว์เซอร์ เห็นกันเคลื่อนที่ใน Hub, ออกจากเกมแล้วตัวละครหายจาก presence, กลับเข้าเกมได้, frame rate/traffic อยู่ในเป้าหมายที่ M0 ระบุ

### M4 — ปาร์ตี้และดันเจียนร่วม

**งาน:** ชวน/รับปาร์ตี้ 2–4 คน, หัวหน้าปาร์ตี้, instance ดันเจียน, ศัตรู/บอส/turn order, คำถามแยกคนและซ่อนคำตอบจนแต่ละคนล็อกคำตอบ, คำสั่งช่วยทีมที่ไม่เปิดเฉลย, reconnect กลางการต่อสู้, สรุปรางวัลรายคนแบบ idempotent, กรณีผู้เล่นออกกลางทาง

**Routing:** Sonnet/medium ทำโค้ด; Opus/high ตรวจ race condition/รางวัล/ความเป็นเจ้าของ run; Sonnet/high แก้บั๊กข้ามระบบที่พบจริง

**ผ่านเมื่อ:** 2–4 คนเข้าดันเจียนเดียวกัน, จบ/แพ้/หลุดแล้วสถานะทุกคนถูกต้อง, ไม่เห็นคำตอบเพื่อนก่อนตอบเอง, ไม่ได้รับรางวัลซ้ำจาก concurrent requests, e2e หลายบัญชีผ่าน

### M5 — โลก เนื้อหา และเศรษฐกิจเกม

**งาน:** พื้นที่ล่า 4 วิชา, ระดับมอนสเตอร์/การเกิดใหม่/Elite, NPC/เควสต์รายพื้นที่, loot table, อุปกรณ์/rarity ที่ไม่ครอบผลการเรียน, ร้านค้า/เงินในเกม, crafting, Codex, บอส/กิจกรรมรายวันและสัปดาห์, data schema และเครื่องมือเพิ่มเนื้อหา, สายอาชีพขั้นสูงเมื่อ 4 อาชีพแรกสมดุลแล้ว ใช้เฉพาะโจทย์ที่ครูอนุมัติสำหรับ production

**Routing:** Sonnet/medium เป็นหลัก; Haiku/low สำหรับข้อความจำนวนมากที่มีเกณฑ์ชัด; Opus/medium เมื่อสมดุลหลายระบบขัดกัน

**ผ่านเมื่อ:** ผู้เล่นเลือกพื้นที่ตามวิชา ล่า/รับเควสต์/เก็บของ/อัปอุปกรณ์/กลับเมืองได้; economy ไม่มีทางปั๊มเงินหรือของจากการส่งซ้ำ; เนื้อหาใหม่เพิ่มจากข้อมูลได้; Subject Mastery ยังวัดแยกจากพลังต่อสู้

### M6 — ความปลอดภัย การดูแล และเตรียมเปิดใช้

**งาน:** เครื่องมือครูตรวจ/ถอนโจทย์, แดชบอร์ดความชำนาญแบบจำกัดสิทธิ์, ระบบข้อความสำเร็จรูปและรายงานพฤติกรรม, การจำกัดคำขอ/ป้องกัน abuse, การสำรองและกู้ข้อมูล, telemetry ที่เก็บข้อมูลเด็กเท่าที่จำเป็น, load test, error monitoring, CI/deploy และคู่มือปฏิบัติการ ทำขั้นนี้ก่อนเปิดให้ผู้เล่นจริงจำนวนมาก

**Routing:** Sonnet/medium ทำงานชัดเจน; Opus/high ตรวจสิทธิ์/ความปลอดภัย/การส่งรางวัล; Sonnet/high แก้ปัญหาประสิทธิภาพที่วัดได้

**ผ่านเมื่อ:** ครูเห็นเฉพาะห้องที่รับผิดชอบ; โจทย์ draft ไม่หลุดเข้ารอบ production; audit หลักผ่าน; load test ถึงเป้าหมาย M0; มือถือและคอมเล่นเส้นทางสำคัญได้; มีแผน rollback

## เริ่มงานแต่ละรอบ

- ถ้ายังไม่มี M0 ให้ทำ M0 เท่านั้น
- ถ้ามีแผนแล้ว ให้เลือก milestone แรกที่ยังไม่ผ่าน ทำงานนั้นเท่านั้น
- ถ้าต้องใช้ secret, บัญชี Supabase, สิทธิ์ deploy หรือไฟล์โจทย์ที่ยังไม่มี ให้ทำส่วนที่ไม่ติดก่อนและระบุอินพุตที่ต้องการอย่างเจาะจง ห้ามสร้างค่าปลอมแล้วรายงานว่าออนไลน์จริง
- ก่อนส่งงาน ตรวจว่าผลลัพธ์เล่นได้ตามเกณฑ์ผ่านของ milestone นั้น ไม่หยุดแค่สร้างโครงไฟล์หรือเขียน TODO
